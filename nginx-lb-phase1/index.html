Nginx-反向代理流程

一、 四个关键阶段

:one: 入口阶段（客户端 → Nginx）

客户端（如浏览器）向Nginx服务器（通常监听80或443端口）发起HTTP/HTTPS请求。Nginx的监听模块接收请求，并根据server_name和listen指令确定处理该请求的虚拟主机。

Listen 层

  1. 基础监听 80
  1. 指定 IP + 端口
  1. 同时监听 IPv4 + IPv6
  1. https

开启ssl ，必须配合证书

  1. HTTPS + HTTP/2
  1. default_server（兜底站点）

常用于丢弃非法请求

  1. reuseport（高并发优化）

满足任意一条：

  • QPS ≥ 1万
  • CPU ≥ 4核以上
  • worker_processes > 1
  • 出现以下现象：
    • CPU 利用率上不去（比如 30%-40% 卡住）
    • nginx worker 有锁竞争（accept_mutex）
    • 高并发下 RT 抖动

👉 这是典型 accept 竞争瓶颈

✔ 结论：必须开 reuseport

这两个机制解决的是同一个问题的不同阶段：

👉 多 worker 如何高效接收新连接（accept）

设计层级完全不同：

  • accept_mutex：Nginx 用户态控制

    每个 worker 拥有独立监听 socket，由内核做负载均衡，真正并行 accept

  • reuseport：内核态负载均衡

    👉 核心思想：

    多个 worker 共享一个 socket，但同一时刻只允许一个去 accept

✅ 现代 Linux（内核 ≥ 3.9）

👉 优先用 reuseport，禁用 accept_mutex

⚠️ 老系统 / 特殊限制

👉 用 accept_mutex 兜底

有 reuseport 时不要用 accept_mutex

👉 accept_mutex 是“补丁式优化”（避免惊群）
👉 reuseport 是“架构级优化”（直接消灭竞争）

  1. backlog（连接队列调优）

解决“连接还没被 accept 前，排队能力”的容量问题.

  1. TCP 连接队列结构（核心）

一个监听 socket 有两个队列：

  1. 三次握手 客户端 → ACK 完成后 进入accept队列

    backlog控制的是accept 队列长度（全连接队列）

  2. 队列满会发生什么？

accept 队列满

  • 新连接会被丢弃
  • 或客户端看到：

SYN 队列满

  • SYN 被丢弃
  • 触发 SYN flood 防护

配置,backlog 不是最终值，还会被内核限制

Server 层

  • 多域名
  • 通配符前缀（子域名）
  • 通配符后缀（不常用）
  • 正则匹配

  • 捕获所有未匹配域名（兜底）

其他配置参数

  1. 字符集类

👉 设置响应内容的字符编码

⚙️ Nginx 会在响应头加：

不会自动转码！（只声明编码） 如果后端是乱码，这个没用

  1. 请求体控制 client_*
client_max_body_size 10m; 限制客户端请求体大小（上传） 文件上传;防止大包攻击
client_body_buffer_size 16k; 控制请求体在内存中的缓冲大小 大量上传请求;减少磁盘 IO
client_header_buffer_size 1k; 单个请求头的初始缓冲区大小;不够 的话→ 用 large_client_header_buffers 请求头较大（JWT / Cookie 很长）
large_client_header_buffers 4 8k; buffer 数量：4，每个大小：8KB 初始不够用，使用这个扩展 buffer
client_header_timeout 10s; 客户端发送 header 的超时时间 防慢速攻击；防止连接被拖死
client_body_timeout 10s; Nginx 等待客户端发送 body超时时间 防止慢速攻击; 太小 → 正常用户上传失败
keepalive_requests 100; 一个连接最多处理多少个请求 防止长连接资源占用;防止连接“老化”
keepalive_timeout 65s; HTTP 长连接保持时间 提升性能（减少 TCP 握手）
send_timeout 30s; Nginx 向客户端发送响应的超时 客户端如果读取很慢，Nginx 断开连接

二、 相关参数说明

「accept_mutex」

accept_mutex 是 Nginx 在多 worker 模型下，用来 避免“惊群效应”（thundering herd） 的一种互斥锁机制。

问题背景：为什么会有锁竞争？

Nginx 是 多 worker 进程模型：

  • 一个 master
  • 多个 worker（通常 = CPU 核数）

所有 worker 共享同一个监听 socket（listen fd）

当有新连接到来时：

👉 内核会唤醒 所有 worker 进程

这就导致一个问题：

❗ 惊群效应（Thundering Herd）

多个 worker 同时被唤醒：

  • 只有 一个 worker 能 accept 成功
  • 其他 worker：
    • 被唤醒 → 抢锁 → 失败 → 再睡眠

👉 造成大量 无效上下文切换 + CPU 浪费

上下文切换 = CPU 从一个进程/线程切换到另一个时，保存和恢复执行现场的过程

包括：

  • 寄存器（PC、SP 等）
  • 内核栈
  • 内存映射信息
  • 调度状态

“抢 accept” vs “抢锁”

从高成本竞争（内核 accept）变成：低成本竞争（锁）

对比项 抢 accept 抢锁
竞争位置 内核态 用户态 + 少量原子操作
是否触发 accept syscall 所有 worker 只有一个
上下文切换 多 少
CPU 消耗 高 低

accept_mutex 作用

开启后：

👉 同一时刻只允许一个 worker 去 accept 连接

工作细节：

  1. 不是一直持锁

worker 不会一直霸占锁，而是：

  • 抢到锁 → accept 一批连接
  • 到时间（accept_mutex_delay） → 释放锁

默认：

👉 每 500ms 轮换一次“接客权”

  1. 轮询调度（近似公平）

worker 之间轮流获取锁：

避免某个 worker 一直独占

什么时候会出现“锁竞争明显”

1️⃣ 高并发短连接

  • HTTP 1.0
  • 没有 keepalive

👉 连接频繁创建 → accept 频繁 → 锁争抢激烈

2️⃣ worker 数量过多

  • worker > CPU 核数

👉 抢锁的人多 → 竞争激烈

因为：

其他 worker：没有CPU一直抢不到锁 → 空转

3️⃣ accept_mutex_delay 太小

👉 锁频繁切换 → 抢锁更频繁 → 抖动
